# Offload stations: the LP0 files from an SD card

Design for phase 42, asked for by Tim on 2026-10-15: the OpenCollar Edge firmware is gaining LP0, a raw LoRa path by which a tracker offloads its flash log to a nearby offload station, a RangerEdge with a battery board and an SD card. Several stations stand in an animal's home range (the case in hand: a CollarEdge on a pygmy hippo fixing every 15 minutes); when the tracker comes within range the records it has not offloaded yet go to the station's card. Protect must take the files from those cards and process them as it processes a raw log file: the records decoded, matched to the tracker, deduplicated against what came over the air, with the reception metadata kept. Decisions D319 to D324 were asked and taken on 2026-10-15, the recommended answer each time, with one correction from Tim the same day: the LP0 address and keys are provisioned per device, not per network, so they live on the device (D320). This document is the plan; O1 to O7 were built on 2026-10-15 (section 11 says where the build departed from the text), O8 is open.

## 1. What the firmware does, as the code reads

Read on 2026-10-15 from `SmartParksOrg/smartparks-opencollar-edge-fw`, branch `fix/existing-lp0-implementation` (68 commits ahead of `main`, which is at 8.0.3; the branch's changelog lists the work under Unreleased; the last commits of 2026-10-14 and 2026-10-15 add CMDQ cohabitation and the LoRaWAN, Bluetooth and satellite confirmation of offloaded records): `app/src/lp0/README.md`, `lp0_offload/lp0_offload.c` and `.h` (the station's SD writer), `docs/reviews/lp0-wire-format.md` (protocol version 4 of 2026-10-07), the master implementation plan's sections on device roles, record identity, addressing and the importer, `docs/reviews/sd-card-primary-source-research.md`, `scripts/ttn_decoder.js` (the port 23 and port 29 decoders), and the public `smartparks-lp0-replay-app` (`make_test_log.py`, the LoRaWAN 1.0 framing reference).

**Roles.** `lp0_node_params[0]` is the role: 0 off, 1 tracker, 2 station. Every supported device type can be a tracker; only a RangerEdge or RangerEdge AirQ with the Artekit AK-SDFS-UART reader (`CONFIG_SDFS_UART_MODULE`) can be a station. Trackers and stations share the discovery frequency and PHY (`lp0_tx_frequency_hz`, `lp0_rx_frequency_hz`, `lp0_communication_params`), the channel plan and the station count (`lp0_node_params[2]`, [3]). Each tracker carries its own LP0 DevAddr, AppSKey and NwkSKey (`lp0_dev_addr`, `lp0_app_key`, `lp0_network_key`), provisioned per device like its DevEUI (Tim, 2026-10-15); the station learns the address during discovery. The tracker's DevEUI travels in discovery and in the station's logs, never in the SD file. The branch as read on 2026-10-15 calls the keys "common", authenticates DISCOVER with the station's own configured NwkSKey and rebuilds every saved frame with the station's configured keys (`lp0_codec_replay_encode`). Tim's firmware issue 772 of the same day ("LP0: separate master-key link authentication from per-device encrypted offload payloads") sets the direction this plan builds for: a deployment-wide `lp0_master_key` authenticates the link (discovery, DATA integrity, the receipts) through per-session keys derived from the discovery transcript; each collar encrypts its records before LP0 with its own unique DevAddr, NwkSKey and AppSKey under LoRaWAN frame counter and MIC semantics; the station treats the result as opaque bytes, may keep routing metadata (the device EUI or DevAddr, counters, times, lengths, the RF reception) and holds no device key; the backend identifies the device and decrypts with its unique credentials; the Semtech-style JSONL contract stays where feasible, versioned where it must change. Open in the issue, and so open here: whether the card holds complete LoRaWAN PHYPayloads or a versioned encrypted-record envelope, the exact counter semantics across transports, and which of the device's credentials are used (the issue names the existing LoRaWAN or satellite ones). Protect's side is built on the ordinary frame the station writes today and is ready for each open point as section 11 says.

**A visit.** The tracker sends DISCOVER on port 33 with its EUI and a fresh nonce; every idle station answers OFFER in its slot; the tracker keeps the strongest OFFER at or above the minimum RSSI (`lp0_signal_checks`, default -100 dBm, with a 20 dB margin over the background and a CAD veto), sends SELECT, gets ACCEPT with the final PHY, both switch to the station's own channel, and the tracker sends its flash records in DATA windows of up to five frames on port 29. The station writes every frame to the card at once and answers a saved-frame bitmap; the tracker marks the records of a confirmed frame as confirmed over LP0 (one bit per medium: satellite, Bluetooth, LoRaWAN, LP0) and the next visit resumes oldest first from the unconfirmed ones. A lost receipt means a repeated frame and a duplicate line on the card: the firmware does not deduplicate anywhere and says so ("deduplication belongs to later processing"). Three weak packets in a row end a visit; the rest waits for the next.

**The card.** Files live in numbered folders, `LOG_1`, `LOG_2` and so on, 64 files per folder, named `STATIONEUI_timestamp[_NNN].jsonl` with the station's EUI in sixteen uppercase hex digits, the Unix second of the first frame's reception, and a collision suffix. One file takes every frame of every tracker whose session opened within 900 s of its first frame, capped at 4 GiB minus 5 MiB, so a file is a quarter of an hour of reception, not a tracker or a visit. Each line is the Semtech UDP `rxpk` document the replay app forwards to a network server:

```json
{"gatewayEui": "0016C001F0ABCDEF", "rxpk": {"time": "2026-10-12T08:50:31Z", "tmst": 1791795031, "freq": 864.629000, "chan": 0, "rfch": 0, "stat": 1, "modu": "LORA", "datr": "SF7BW250", "codr": "4/5", "rssi": -71, "lsnr": 9, "size": 64, "data": "QAMCASYAZQAd..."}}
```

`gatewayEui` is the station, `time` and `tmst` the station's reception time (`tmst` is Unix seconds, not the microsecond counter the field means at a gateway), `freq` in MHz, `datr` the spreading factor and bandwidth, `rssi` in dBm and `lsnr` in dB as whole numbers, `data` the frame. The station strips the LP0 session envelope and rebuilds `data` as an ordinary LoRaWAN 1.0 uplink: MHDR `0x40`, the tracker's DevAddr, FCtrl, a 16-bit frame counter (the upper half of the 32-bit counter is zero), FPort 29, the FRMPayload encrypted with the tracker's AppSKey, the MIC with its NwkSKey. The address is in the clear; nothing else is readable without the keys. The FRMPayload is the normal flash record stream `[port][msg_id][len][data][store time u32]` repeated, at most 228 bytes per frame, without the per-medium flags byte: the same bytes the port 29 uplink, the Bluetooth flash read and the raw log file carry, which `_decode_flash_log` in the OpenCollar driver already parses. Since firmware 8.1 a station also broadcasts a statistics message on port 23 (msg `0x9D`, 99 bytes: the card detected and writable, the SD worker's state, uptime, 21 cumulative counters of visits, frames, bytes and errors) under its own DevAddr; idle stations archive each other's broadcasts to the card in the same JSON, and a station's own report may sit inside its port 29 records when its flash mask selects it.

**The clocks.** A record's store time is the tracker's clock, as in every flash stream. The line's reception time is the station's clock, which comes from a fix or from `init_time` plus uptime, so a station that never fixed writes a time years off.

**What the firmware does not do.** No record ids (dropped on 2026-10-02 in favour of the five-frame bitmaps), no tracker EUI in the file, no deduplication, no automatic upload: the card is carried to a computer. The research document's section 3.17 of 2026-09-03 describes an earlier LP0 and says to ignore it; it is superseded by this document and is rewritten in task O7.

**The replay path that exists today.** The replay app reads these files and forwards each line to a Semtech UDP gateway bridge, so a ChirpStack with the trackers registered as ABP devices under their own LP0 keys decodes the frames on port 29, and Protect's ChirpStack adapter would then receive them like any uplink. That path was considered and not chosen (section 2).

## 2. Why Protect reads the card itself

Protect could leave the cryptography to a network server: replay the card into a ChirpStack through the replay app and let the ChirpStack source deliver the frames. Three things speak against it. A network server enforces frame counters: a replayed card holds frames out of order and behind the counter the server last accepted, and the firmware's own plan calls the TTN replay procedure unqualified; a card that fails to replay would lose data silently. The LP0 keys of every tracker would live in a ChirpStack beside Protect's own copy, and the trackers would have to exist there twice (OTAA for the air, ABP for the cards), which TTN forbids and ChirpStack tolerates by making two devices of one. And nothing in Protect would know that a frame came from a card, from which station, with which reception, or that a card was read at all. Reading the file directly costs one small codec (section 5) and reuses the whole raw log file path: the managed asset with its status and counts, the file worker with its batches and progress, the decoder's flash stream path that keeps stored times, the canonical keys that fold a record delivered twice into one with two deliveries, and Needs attention for a tracker nobody named.

| D319 | An offload station is an entity with its device, and a gateway of the LP0 source | The RangerEdge is a device as today. It is assigned to an entity of the new Equipment sub-type **Offload station** (`offload_station`, icon `device.lora_gateway`), which gives it a name, a place set by hand (D261, the place of the device), a marker on the map, a picture and rules. Over a gateway alone (nothing to name or alert on) and over an entity alone (no receptions, no coverage). Tim, 2026-10-15. |
| D320 | The LP0 address and keys live on the device; a built-in source carries the files and the identities | Every tracker has its own LP0 DevAddr, AppSKey and NwkSKey, provisioned per device as its DevEUI is. Setting the address writes the device's external identity on a built-in data source "Offload station files" (adapter `lp0_station`, `builtin`, a fixed id as the log file and WebBLE sources have, decision D77), with `identity_type` `dev_addr` and the address as external id (eight uppercase hex digits as the firmware and an LNS print it, the big-endian form); every card's lines are deliveries on that source and every station is a gateway of it. A frame from an address no device has is retained unassigned and listed on Needs attention, where it is linked to the device, as an unknown DevEUI is (D96, D121), and its keys are entered on that device; "Create device" is offered too, with the keys to follow. Over a data source per LP0 network holding one pair of keys, which was the first proposal and which Tim corrected: the keys are unique per device. Tim, 2026-10-15. |
| D321 | The files are raw log files of the station, decoded through the one pipeline | A card's files are uploaded on the station's device page or on the built-in source's page, one JSONL at a time or a zip of the `LOG_*` folders; each JSONL becomes a `device_log_files` row with the station as its device, channel `lp0` and the folder in its attributes (the same card, progress bar, counts, download and re-decode as a raw log; a zip is unpacked by the API into one row per file). The decoder's file worker reads a line, stores it as a source event of the built-in source with the DevAddr as external id, `acquisition_channel` `lp0`, `ingestion_method` `file_upload`, one gateway reception for the station, `network_received_at` from the line (D324) and `file_uploaded_at` from the row, and decodes it. The decryption is one step of the pipeline, not of the file worker: before the driver runs, a source event of channel `lp0` without `frame_hex` is unwrapped by the adapter with the device's own credentials, which verifies the MIC with the device's NwkSKey and decrypts the payload with its AppSKey (LoRaWAN 1.0, the counter's upper half zero), writing `frame_hex`, `f_port` and `mic_ok` into the provider metadata (the payload, the line as stored, is never changed), so the driver's LoRaWAN path reads it; the same step serves the walk over retained frames after an address is linked (D121) and "Decode again". A frame of a device without keys fails with `CREDENTIALS_MISSING` (user actionable: "set the LP0 keys on the device, then decode again"); a frame whose MIC does not verify fails with `PAYLOAD_DECODE_FAILED` ("the frame does not verify under this device's keys"), counted as malformed, never guessed. A frame with the same DevAddr, counter and bytes as one stored for this source in the last 30 days is the firmware's repeat after a lost receipt: stored as `duplicate` of the first and not decoded again, as a satellite redelivery is (D160); a record that also came over the air or from another card is one record with several deliveries through its canonical key. Recorded by Claude, 2026-10-15. |
| D322 | The reception metadata of every line is kept and shown | Per source event: the station EUI, the reception time, RSSI, SNR, the frequency, the spreading factor and bandwidth, the coding rate, the frame counter, the file and the line. The traffic tables' Details column reads them for channel `lp0` (station, RSSI and SNR, SF and BW, the records in the frame); the source event dialog shows the line; the tracker's Connectivity tab gets an **Offload** block per LP0 source (stations heard in the period with frames and records each, the best station and its share, the last offload, repeated frames); the station's page gets an **Offload station** card (files received and their folders, frames and records, the trackers served in the last 30 days, the last visit, and the port 23 state). | D323 | The port 23 statistics message is decoded now | `_decode_lp0_statistics` in the OpenCollar driver: msg `0x9D`, body length 97, version 1, the value and known bitmaps (an unobserved bit is unknown, never false), uptime, pending and high-water SD jobs, the 21 counters in the README's order; a state `lp0_station` with the eleven observations and measurements `lp0_<counter>` in a new metric category `offload` seeded in the registry; health lines "SD card" (critical when the card is absent or not writable, warn when unknown or when the storage queue is full) and "Offload visits"; a rule template "Offload station without a card". Over waiting for the release. Tim, 2026-10-15. |
| D324 | A station's reception time is believed only when it is plausible | A line's `time` earlier than `LP0_EARLIEST_RECEPTION` (2024-01-01) or later than the upload is a clock the station never set; the frame then carries no `network_received_at` and the clock rules of D119 judge the records against the upload time, as they judge a raw log file. The line's time is kept in the provider metadata either way. Without this a station without a fix would have every record of every tracker marked invalid as "ahead of its delivery". Recorded by Claude, 2026-10-15. |

## 4. The data flow of a card

1. **The credentials.** On each tracker's device page, the LP0 card takes the address and the two keys (D320); saving writes the device's `dev_addr` identity on the built-in source. A device whose settings readback carried `lp0_dev_addr`, `lp0_app_key` and `lp0_network_key` (the settings table of D228) offers "Use the device's reported values" with a confirmation, since the readback is the device's own word. The keys are shown and changeable by whoever may set them; a viewer sees only that they are set.
2. **The upload.** `POST /devices/{id}/log-files` takes a JSONL file or a zip on the station's device page (the `LOG_*` folders of a card, read with `zipfile` in the API, every `*.jsonl` member a row, other members ignored and named in the response; a file whose name holds another station's EUI is accepted with a note); `POST /data-sources/{id}/log-files` takes the same on the built-in source's page for a card whose station is not a device in Protect yet. Each row: the station from the file's name (its EUI, matched to a device by serial number or a `dev_eui` identity; a name that matches no device leaves `device_id` on the row's source and the station unknown, noted in the attributes), channel `lp0`, the folder, the file's SHA-256 (the same file twice is refused with 409 as today). The limit stays `LOG_FILE_MAX_BYTES` per file and a zip of at most `LP0_ZIP_MAX_BYTES` (512 MB).
3. **The split.** `parse_station_jsonl` in `shared/logfiles.py`: one line is one `StationFrame` (the station EUI, the reception time, RSSI, SNR, frequency, data rate, coding rate, the frame's bytes); a line that is not JSON, lacks `rxpk.data` or whose base64 does not decode is an error with its line number; blank lines are skipped. The firmware writes every line with a leading newline, so the first line of a file is empty.
4. **The frame.** `shared/connectivity/adapters/lp0_station/lorawan.py`: `parse_uplink` (MHDR must be `0x40` or `0x80`, DevAddr little-endian in the frame and reported big-endian, FCtrl with its FOpts length, the 16-bit counter, FPort, FRMPayload, MIC), `verify_mic` (AES-CMAC under the device's NwkSKey over B0 and the frame, the 32-bit counter with its upper half zero) and `decrypt_payload` (AES-128 in the LoRaWAN counter construction under the device's AppSKey, or the NwkSKey on port 0). The file worker parses the header alone (the address and the counter are in the clear); the keys are applied in step 6. The golden test is the firmware's own fixture: the saved replay packet of `docs/reviews/lp0-wire-format.md` under its synthetic keys verifies and decrypts to the three-record stream the document gives (checked with the `cryptography` library on 2026-10-15; no new dependency).
5. **The delivery.** An `InboundMessage` per line: `external_id` the DevAddr, `identity_type` `dev_addr`, `event_type` `uplink`, the payload the line's document as stored (immutable, D8), the provider metadata with `dev_addr`, `f_cnt`, `f_port`, `station_eui`, `received_at`, `rssi`, `snr`, `frequency_hz`, `data_rate`, `coding_rate`, `log_file_id` and `line`; one `GatewayReceptionData` for the station with RSSI, SNR and frequency (`upsert_gateways` makes the gateway row on the built-in source, D66); `network_received_at` when plausible (D324); `file_uploaded_at`; no `device_id` from the caller, the identity decides. `store_inbound` resolves the identity, applies the repeat rule of D321 (`_lp0_redelivery` beside `_satellite_session`: the same source, DevAddr, counter and payload digest within 30 days), writes the trace step "offload frame" with the station and the signal, and the file worker decodes the event in the same transaction as today, `LOG_FILE_BATCH_SIZE` frames or three seconds per commit. A line whose address no device has stays `unassigned` on the row, as any unknown identity's event does.
6. **The unwrap and the decode.** `process_source_event` runs the adapter's `unwrap_frame(event, credentials)` for a channel `lp0` event without `frame_hex`: the device's credentials are read (one read per device per batch), the MIC verified, the payload decrypted, and `frame_hex`, `f_port` and `mic_ok` written to the provider metadata, with a trace step "frame unwrapped" naming the counter and the port. Then the OpenCollar driver treats channel `lp0` as it treats LoRaWAN: `f_port` 29 is the flash stream (`_decode_flash_log`, `records.stored = True`, the layout from the records' own status messages), 23 the statistics message (D323), another port a live message filed at the line's reception time. `delivers_live` stays LoRaWAN only, so D259's clock-behind rule does not touch a card. The pipeline attributes every record at its own time, links repeat deliveries to the canonical row, updates the tracker's current state only with what is newer than it (a card of last month moves nothing back), and publishes `position.created` for records nothing had seen.
7. **The counts.** The row's `frames_total`, `frames_done`, `frames_failed` (unreadable lines and frames that do not verify), `records_found`, `records_new`, `records_duplicate`, the period and the firmware as today; the attributes gain `trackers` (per DevAddr: the device when known, frames, repeats, records new and known, and `without_keys` when the device has no credentials yet) and `unknown_dev_addrs`. The Needs attention summary counts the unknown identities of the source; "Link" to a device walks the retained frames through the decoder (D121), which unwraps each with that device's keys and lands the records; a device linked before its keys are set fails its frames with `CREDENTIALS_MISSING`, and "Decode again" on the file takes them up once the keys are there.

Bounds: a file of at most `LOG_FILE_MAX_BYTES` (64 MB, about 100,000 lines), a zip of at most 512 MB unpacked file by file, a batch per transaction, one reception per frame (the receptions hypertable is compressed by gateway; a card's receptions all belong to one station, so a card decompresses one segment), at most 32 records per frame by the wire format. A 15-minute window of one tracker at full rate is about 400 frames; the dev test's largest snapshot (6,607 records) is about 830 frames and 450 KB of JSONL.

## 5. Framework and core changes

- **The adapter.** `shared/connectivity/adapters/lp0_station/__init__.py` (`key` `lp0_station`, label "Offload station files", `push` false, `builtin` true with a fixed `SOURCE_ID` created by migration 0053 as 0011 created the log file and WebBLE sources, `acquisition_channel` `LP0`, no credentials, no event connector, no command connector, a `setup_hint` saying the keys live on each device, `identity_type` `dev_addr`, `unwrap_frame(event, credentials)` as the one place a frame is verified and decrypted) and `lorawan.py` (the codec of section 4, pure, typed, no ORM); registered in `shared/connectivity/registry.py`. `AcquisitionChannel.LP0 = "lp0"` and the frontend's `channelLabel` ("Offload station"). `tests/shared/test_provider_boundary.py` keeps holding: the adapter name lives only under `adapters/`.
- **The credentials per device.** Migration 0053: `device_lp0_credentials` (device id as primary key, `dev_addr` unique, `app_s_key` and `nwk_s_key` as Fernet tokens, `set_by_user_id`, `set_at`, `source` `person` or `device`). `shared/domain/lp0.py` holds `set_credentials` (validates 8 and 32 hex digits, encrypts, writes or moves the device's `dev_addr` identity on the built-in source through `ensure_channel_identity`'s sibling `ensure_address_identity`, refuses an address another device holds with a 409 naming it) and `credentials_for(session, device_id)` (decrypts for the pipeline). `PUT` and `DELETE /devices/{id}/lp0-credentials` (`devices:control` in the device's project, or a server admin; audited as `device.lp0_credentials_set`), `GET /devices/{id}` carries `lp0_dev_addr` and `lp0_keys_set`; `components/devices/Lp0CredentialsCard.tsx` on the device page, with "Use the device's reported values" when the settings table holds the three `lp0_*` readbacks.
- **Identities by address.** `ExternalIdentity.identity_type` already exists; `resolve_identity` takes the message's `identity_type`; Needs attention's "Link" and "Create device" accept `dev_addr` identities, the created device named after the address and left without keys until a person sets them; `protect_api/serial.py` leaves the serial empty for an address, since a DevAddr is not a serial (D101).

- **The reads.** `_lp0_link` in `routers/devices.py` beside `_lorawan_link` and `_iridium_link` (per LP0 source: the stations heard from the receptions of the period, frames and records per station from the source events, the best station's share, the last offload, repeats), `SourceConnectivity` with an `offload` block, `components/devices/ConnectivityCard.tsx` renders it; `TrafficRow` carries the LP0 metadata and `TrafficTable.tsx` details it; the source event dialog shows the line; `lib/positionKind.ts` is untouched (a record from a card is the device's own fix).

## 11. As built, 2026-10-15

O1 to O7 landed in one session, in the order of section 7, after Tim's correction that the keys are per device. Where the build departs from the sections above:

- **No upload on a data source page.** A card is uploaded on the station's device page alone (`POST /devices/{id}/offload-files`, from the Log files card, which takes a `.jsonl` or a zip beside a raw log). A row of `device_log_files` needs a device, and the station is a RangerEdge with a DevEUI that is made as any device; a card of a station that is not a device yet waits for the device. The built-in source has no page of its own.
- **The station's own identity.** A station's files create no `device_id` identity for the station on the offload source (as a raw log file does on the log file source): the station is a gateway of that source, not a device reporting on it. Its trackers' identities are by address.
- **The repeat rule keys the frame, not the line.** The station writes the reception time into every line, so a repeated frame is a different line; `_lp0_repeat` compares the SHA-256 of the frame bytes (`phy_sha256` in the provider metadata) under the same address and source within 30 days.
- **Two status bits bear the decoder's names.** The branch's `decodeLP0Statistics` names bits 5 and 6 `lp0_enabled` and `lp0_listening`, where the README says `enabled` and `listening`; the driver follows the code, which the test runs with node.
- **A bool health line can have a threshold.** `lp0_sd_card_ok` is a yes or no that is critical when no; `_level_of` in `shared/domain/health.py` levels a bool by `critical_below` and `warn_below` now, which no earlier field used.
- **The walk's reception window.** The decoder's walk over retained frames linked the receptions of an event within a day of its ingestion; a card's receptions lie weeks before its upload, so `unlinked_receptions` takes the oldest reception time of the page as well.
- **A station file's frames belong to other devices.** `_existing_frames`, which finds a file's stored frames for a re-decode and for resuming an interrupted run, matched on the file's device; for a station file it matches on the file alone.
- **The error code is in a check constraint.** `application_errors` checks its codes, so migration 0053 admits `CREDENTIALS_MISSING` beside the `lp0` channel on `device_log_files`, `source_events` and `source_deliveries`. The migration ran in under a second on the local database with a compressed chunk; on the dev server the two hypertables are large and the constraint rebuild is the step to watch.
- **The metrics.** The `offload` category seeds 25 metrics (the bool, uptime, the two SD gauges and the 21 counters) through `seed_sql`, as 0048 seeded the physiology ones.
- **Checked.** `ruff`, the formatter and `mypy` clean; `tests/shared`, `tests/decoder`, `tests/rules` and `tests/api` (244 passed) against the local compose stack; the frontend's type check, lint (the 21 warnings that were there, plus none), 262 Vitest tests, both catalogues complete (the Dutch written by hand for 64 strings); the strict docs build and the docs check; the OpenAPI schema regenerated.

**Firmware issue 772, the same evening.** Tim's issue sets the authentication model: a deployment master key for the link, per-device credentials for the payload, the station opaque, the backend decrypting with each device's own keys. The build already does the last three; three things were added for the issue's open points:

- **A counter across a rollover.** The frame carries the counter's low 16 bits; the issue asks for correct LoRaWAN counter semantics. `unwrap` tries the upper half zero (today's 16-bit mode), then the upper half of the device's last verified counter and the next one, as a LoRaWAN receiver does; the MIC decides and nothing else is guessed. The newest verified 32-bit counter is kept on the device's credentials (`last_f_cnt`, `last_frame_at`) and the frame's 32-bit counter in its metadata (`f_cnt32`).
- **A frame format named is a frame format checked.** A line that names its format (`frameFormat`, `format` or `lp0Format`) is read only when it is one this version reads (`lorawan`); an envelope the firmware may introduce is refused by name, never guessed at, and the adapter's `unwrap_frame` is the one place a second format would be added.
- **The tracker's EUI as the station's word.** A line that carries the tracker's EUI (`devEui`) keeps it on the frame and names the unknown identity with it on Needs attention, so a person sees which device an address belongs to; the identity stays the address and the keys decide, the EUI is never used to link by itself.

Which of the device's credentials the firmware will use (its own LP0 pair, or the LoRaWAN or satellite session keys) changes nothing in Protect but the words on the card: the three values set on the device are whatever the device encrypts its offloaded records with.
